# Architecture

## Modèle de données d'un build
```js
{
  name: 'Tank + Soigneur',
  obj:  ['tank', 'healer'],                                  // objectifs : [principal, secondaire] (GOALS) ; [] = arbre libre
  ad:   {sk: {wetDog: 1}, pn: {'pip:1wwtpca': 1}},           // vos ajouts avec objectif (2.3.0) : le combo est recalculé avec eux
  gem:  {w1: 'g_armor', w2: 'g_reap'},                       // gemmes des deux armes (GEMS) ; descriptives
  sk:   {nemesis: 3, ...},                                   // rangs achetés dans l'arbre (imposés + ajoutés)
  pn:   {'pip:1rkw3ke': 1, ...},                             // nœuds d'attribut acquis (identifiant de jeu, base 36 ; source de vérité)
  pip:  {con: 11, ...},                                      // comptes dérivés de pn par syncPips()
  lvl: 50, exp: 114, flame: 11,                              // niveau, points d'exploration, Flamme
  gear: {}, upg: 5,                                          // INERTES (2.0.0) : équipement d'un ancien lien, relu et réécrit tel quel
  tv: 1                                                      // build fait sur le tracé réel (absent = build enregistré avant la 1.9.0 → migré)
}
```
`compute(build)` renvoie `attr` (nœuds + Flamme + Rôdeur), `hp`, `mana`, `sta` et `R(id)` (rang). Ni équipement ni gemme n'y entrent.

## Objectifs (06-objectifs.js)
- `GOALS` : `{id, n, grp, area, gem, steps: [[titre, raison, {compétence: rang | attribut: nœuds}]]}` ; `id` = place figée dans `FZ.goals`.
- `SUPS` (2.1.0) : objectifs de soutien, même forme sans `grp` ni `gem`, compétences seules ; dans `GOALI` avec `sup:1` ; `obj = [p, s]` ou `[p, s, t]`.
- `combo(p, s, lvl, exp, flame, t, A)` (mis en cache, clé = objectifs, réglages et ajouts) : `runGoal` pour le principal, le secondaire puis le soutien ; renvoie la **partie imposée** (`sk`, `pn`, `pip`), `rep` (par objectif : points, étapes `{st: 'ok'|'part'|'no', miss, at, skip}`), `spent` (imposé), `links` (imposé − éléments des étapes), `wpts` (points des éléments atteints), `left`, `want` (rangs visés atteints), `by` (élément → [objectif, étape]), `orphans` / `drop` (ajouts qu'il a fallu relier / qu'aucun calcul ne relie), `tree` (points de tout l'arbre).
- 2.3.0, vos ajouts `A` : `runCombo` part d'un arbre qui les contient (coût nul dans `dijkstra`), compte vos rangs pour les étapes (imposés alors), pas vos nœuds d'attribut (`sp`) ; `cleanLinks` ne retire une liaison que si elle ne coupe aucun nœud relié (`nReach`) ; `linkAdds` relie les ajouts restants (chemin le moins cher, budget dépassé s'il le faut). `overlay` = ancien calcul (combo seul + ajouts) ; `better` garde le meilleur (avancée `wpts`, puis points de l'arbre), si l'ancien calcul est « juste » (n'absorbe ni un de vos nœuds d'attribut ni une de vos liaisons).
- Build : arbre = partie imposée ∪ `b.ad` (`treeOf`). `imposed(b)`, `addsOf(b)` (`b.ad` ; tout l'arbre en arbre libre), `regen(b, keep)` (recalcul ; sans `keep` : ajouts de `drop` élagués, règle 3), `rebuild(b, A)`, `setGoals(b, p, s, t)` (nouveau principal : combo seul et gemmes de l'objectif ; secondaire ou soutien changé : ajouts gardés), `lockOf(b, n)` (rang minimum), `fitGoals(b)` (lien ou build enregistré : ajouts du segment `-a` ou du champ `ad`, sinon arbre − combo seul et recalcul signalé par `b._recalc` ; arbre qui ne correspond pas → objectifs retirés, arbre gardé, `b._objLost` ; propriétés non énumérables).

## Arbre (tracé réel du jeu 1.0)
- `TREE` (01-tree-data.js, généré par `scripts/tree-from-pindrop.mjs`) : `nodes` = `[identifiant de jeu base 36, clé, x, y]` (clé = id de compétence, `@str`… pour un attribut +1, `*` pour un départ), `links` = paires d'indices non orientées. Les nœuds d'attribut y sont rangés, par attribut, du moins cher au plus cher d'accès : cet ordre est leur `idx`.
- `TOPO` (04-tree.js) : nœuds `start` (12 Étincelles, gratuites), `skill` (id de SK), `pip` (`pip:<gid>`) aux coordonnées du jeu × `TREE_SCALE` ; `E` = les 312 liaisons réelles (avec leur longueur) ; `byGid` pour le partage. La Flamme (`hub`) est **logique** : reliée aux 12 départs par `nb` seulement, hors de `E`, jamais dessinée.
- `reach(b)` : parcours depuis la Flamme à travers les départs et les nœuds acquis. `dijkstra(b, R, stop)` : coûts depuis les nœuds reliés (pondérés par les nœuds non acquis) ; `pathTo` et la vue liste s'en servent.
- `normalize(b)` : (1) nœuds d'attribut : clés inconnues retirées, manque comblé par attribut avec les premiers nœuds par `idx` (presets, codes b1/b2, builds 1.8 n'ont que des comptes) ; (2) tout nœud isolé est relié par le chemin le moins cher, un Dijkstra multi-cibles par tour ; (3) les liaisons devenues inutiles et les nœuds d'attribut en surplus sont retirés tant que tout reste relié. `migrate(b, from)` = `normalize` + note non énumérable `b._mig` (ajouts, points) pour la fenêtre « Lien d'avant le tracé réel ».

## Partage (03-share.js)
- `FZ` : tables figées (objets, gemmes, ancien ordre de SK, attributs b1, anciens bits b2, identifiants de jeu des attributs et des compétences pour b3, emplacements d'équipement, objectifs). Ajout en fin seulement ; empreintes vérifiées par share.test.js.
- `b3-<en-tête 8>-<équipement 18>-<masque attributs>-<masque compétences>-<rangs>[-g<gemmes 4>][-o<objectifs 4 ou 6>[-a<masque>-<rangs>]]-<contrôle 2>` : vos ajouts (2.3.0, seulement avec objectifs et s'il y en a) = un bit par nœud possédé dans l'ordre du code (attributs puis compétences) et un chiffre de rang par compétence marquée ; masques en base 36 sur `FZ.at` / `FZ.nd`, un chiffre de rang par compétence possédée (`0` si aucune), objectifs = 2 caractères chacun dans `FZ.goals` (principal, secondaire, puis soutien seulement s'il y en a un, 2.1.0 ; `zz` = aucun ; segment absent = arbre libre), contrôle `b3sum` (FNV-1a modulo 36²). `decode` ne lève jamais d'exception (null si illisible, tronqué ou abîmé), accepte les majuscules, puis `fitGoals`. Un bit sans nœud (version plus récente, ou nœud retiré par un patch) ou un nœud devenu isolé : `migrate(b,'b3')` et fenêtre « Lien fait sur un tracé antérieur ».
- b1/b2 : lus via les tables figées en comptes d'attributs + compétences, puis `migrate`. À l'ouverture d'un tel lien, l'adresse reçoit le code b3 du build migré. Équipement : relu via `FZ.items` / `FZ.slots`, gardé inerte.

## Rendu (10-ui.js, 30-graph.js)
- Une page : `.side` (Vos points, Objectifs, Pourquoi ce combo, Gemmes) et l'arbre (`#p-tree`, collé en haut sur ordinateur) ; A contre B sous la grille (`#p-cmp`, case « Comparer »). Une colonne sous 900 px.
- `renderAll()` = `renderTabs`, `renderPoints`, `renderGoals`, `renderWhy`, `renderGems`, `renderTree` (graphe : `G.refresh()` ; liste : attributs et compétences, « − » désactivé au rang imposé), `renderCmp`. Événements : `pickGoal(i, v)` (menus), `setting(k, v)` (niveau, exploration, Flamme : `rebuild`), `addRank` / `remRank` / `addPipNode` / `remPipNode` / `addPip` / `remPip` / `buyTo` (verrou : `lockOf`, message `imposedMsg` ; avec objectif, via `viaAdds` : `b.ad` modifié, `regen`, message « Combo recalculé »), `saveCur`, `loadSaved`, `fromHash`, `notices` (migration, objectif retiré). `localStorage` (via `lsGet` / `lsSet`) ne sert qu'aux builds enregistrés ; aucune écriture dans le hash hors « Partager » et l'ouverture d'un lien migré.
- Graphe (30-graph.js) : chaque nœud est ancré à sa position réelle ; ressorts à la longueur réelle et rappel constant vers l'ancre : au repos, le tracé est exactement celui du jeu. Glisser un nœud l'étire (élastique), il revient à sa place (immédiatement si mouvement réduit). Libellés GUERRIER / RÔDEUR / MAGE au bord extérieur de chaque zone ; noms placés sans chevauchement par priorité. Nœud acquis plein (couleur de la zone) ; ajouté par l'utilisateur : anneau pointillé (`isAdd`) ; carte : origine (« Imposé par … · étape n », liaison du combo, ajouté) et « − » désactivé au rang imposé. `G.refresh()`, `G.focus(zone)`, `G.resize()` ; l'observateur de `#gwrap` recale le canvas (vue Liste ↔ Graphe, fenêtre). Caché, `W = 0` : rien n'est dessiné.
- Couleurs du canvas lues depuis les jetons CSS (`--g-*`, `--war`, `--rng`, `--mag`, `--core`, `--ember`), relues quand le thème change.

## Tests
`tests/run.mjs` exécute les scripts de `src/js` dans un contexte Node avec un faux DOM (Proxy qui accepte tout), puis les `*.test.js` (`00-aides.test.js` en premier : `fromPreset` pour les codes figés, `fakeLs` / `withLs`, `lostOf`, `keepUi`). `objectifs.test.js` vérifie le moteur (12 objectifs × budgets × Flammes : relié, dans le budget, jamais de recul ; coûts à 212 points ; secondaire ; verrou ; ajouts ; 2.3.0 : cas figés d'ajouts qui libèrent des points, retrait, sans recul et invariant sur plus de 1 000 combos avec ajouts au hasard) ; `codes-figes.test.js` fige les codes des 16 anciens presets. La CI (`tests.yml`, chaque PR) lance aussi `tests/e2e.mjs` (Playwright, Chromium ; `E2E_LONGTASK_MS=500` relève le seuil des tâches longues) et garde les captures 7 jours (artefact « captures-e2e »). Les tests d'interface Node ne vérifient que « pas d'exception » et l'état ; le rendu réel se vérifie avec `tests/e2e.mjs` et ses captures.
